## 3. Verified format knowledge

### 3.1 MT Framework ARC

Header: magic `\0CRA` = **big-endian** (PS3, what Utage uses), `ARC\0` =
little-endian. `u16 version`, `u16 count` at offset 4. Entry table starts at 8
(little-endian adds 4 when version is not 7/8/9).

Standard entry is **80 bytes**: 64-byte NUL-terminated name, then at offset 64
`u32 type_hash`, `u32 compressed_size`, `u32 packed_size`, and `u32 payload_offset`
at name_bytes + 12.

- Big-endian: `raw_size = packed_size >> 3`, `flags = packed_size & 7`
- Little-endian: `raw_size = packed_size & 0x00FFFFFF`, `flags = packed_size >> 24`

Two variants are handled: an **extended 144-byte entry** with a 128-byte name
(detected when the first record's hash/packed/offset at offset 64 are all zero),
and **Switch v9** with an 84-byte entry and payload_offset at 80.

Payloads are zlib. An entry is stored uncompressed when
`compressed_size == raw_size`.

Real archives in `PS3_GAME` confirm: big-endian, version 8, 80-byte entries,
64-byte names. Sample: `battle.arc` 173 entries, `game.arc` 38 entries.

Type hashes seen: `0x241F5DEB` tex, `0x10C460E6` msg, `0x2EA515BF` mif (FIM),
`0x5E0EF076` asc (CSA), `0x1D609FFB` fnt, `0x60DD1B16` lsp.

**Rebuild rule.** `rebuild_arc` keeps every untouched compressed blob byte for
byte, keeps entry order, type hashes, flags and names, re-lays payloads on the
alignment inferred from the original offsets (tries 2048 down to 4), and
rewrites only sizes and offsets.

### 3.2 XET textures

Magic `\0XET`. Dimensions are packed into bytes 8..10 read big-endian:
`width = (v & 0xFFF) * 4`, `height = ((v >> 12) & 0xFFF) * 2`. Format code is
byte 14; `0x14` and `0x19` mean DXT1, everything else is treated as DXT5/BC3.
`u32` big-endian texture offset at 16. Preview works by wrapping the block
payload in a synthetic DDS header and letting Pillow decode it.

### Writing: BC1 and BC3, with a real encoder

`bcn.py` encodes both DXT1/BC1 and DXT5/BC3. The original encoder chose its
two endpoint colours as the brightest and darkest pixel by luma, which is
quick and wrong — the best pair spans the block's dominant axis in colour
space, which is rarely the extremes. The current one:

1. fits a line through each block's colours along their **principal axis**
   (batched power iteration on the covariance);
2. quantises the ends to RGB565 and assigns each pixel the nearest palette
   entry;
3. **re-solves both endpoints by least squares** for the indices just chosen,
   and repeats;
4. scores four candidate endpoint pairs — raw, inset, and each refined — and
   keeps the winner **per block** by measured error, because insetting helps
   most blocks and hurts high-contrast ones;
5. uses BC1's three-colour punch-through mode only where a block actually has
   transparent pixels.

Everything is vectorised over all blocks with numpy. **numpy is now a
dependency.**

**Measured** by `_bcn_validate.py`, which round-trips real game textures (a
good encoder rediscovers nearly the original endpoints, so error here is the
encoder's fault, not the test's):

| | old encoder | this one |
|---|---|---|
| DXT5 mean RGB error | 3.95 | **0.14** |
| DXT1 mean PSNR | — (could not write) | **63.8 dB** |
| head to head, DXT5 | — | **+2.7 to +24 dB, two exact** |

Scores count only visible pixels: RGB under a fully transparent pixel is never
drawn, and including it measures noise rather than quality.

**The bug worth remembering.** `_color_indices` masked palette entry 3 out for
*every* block, not only three-colour ones — so a quarter of the palette was
unreachable in normal four-colour blocks. On a block whose four colours were
exactly the four palette entries, the third colour collapsed onto the second.
It cost about 20 dB and looked like a bad endpoint fit. If quality regresses,
check the index assignment before blaming the fit.

### The real XET header, from Kuriimu2's source

Read from `plugins/Capcom/plugin_mt_framework/Images/MtTexSupport.cs`. Bit
fields are packed **LSB-first inside 4-byte blocks**, each block read in the
stream's byte order — big-endian for this `\0XET` PS3 build:

| offset | fields |
|---|---|
| `0x04` | version 12 · **swizzle 12** · reserved 4 · **alphaFlags 4** |
| `0x08` | mipCount 6 · width 13 · height 13 |
| `0x0C` | imgCount 8 · format 8 · unk3 16 |

The original code guessed `width = (bits & 0xFFF) * 4` and
`height = ((bits >> 12) & 0xFFF) * 2`, which **agreed only by luck on
power-of-two sizes**. It also never read the swizzle field at all. Kuriimu2
applies a `BcSwizzle` on PS3 when that field is set, so a swizzled texture
would have been silently misread as garbage. `xet_info` now parses the real
fields and **raises rather than guessing** if `swizzle` is non-zero.

Measured across the tree: every sampled texture reports `version 151,
swizzle 0, mipCount 1, alphaFlags 2`, so nothing in this game is swizzled —
but the check is there now. Adopting the correct parser changed no results:
3,046 textures decode, 0 fail, identity rebuilds still byte-identical.

**`alphaFlags` is still unused here.** It is the one header field Alrummi 3
does not act on, and it is the most likely explanation for any remaining
difference against Kuriimu2's rendering.

### Colour: what Kuriimu2 shows versus what this decodes

Reported: Kuriimu2 renders `stage_000_ID_HQ` as cream lettering with a gold
outline on black, where Alrummi 3 renders it green. That was investigated
rather than assumed, and **no decode fault was found**:

- Byte-swapping the RGB565 endpoints (the obvious big-endian suspect) produces
  visibly corrupt output, not gold.
- Byte-swapping the colour index word, reversing the alpha index bytes,
  reversing their bit order, and swapping the alpha endpoints all leave the
  image essentially unchanged.
- Every one of the **nine copies** of that texture across the Utage tree
  decodes to the same green, and so do all **five copies in Samurai Heroes**.
- Channel permutations (BGR, GRB, GBR, RBG, BRG), un-premultiplying alpha, and
  swapping alpha with a colour channel all produce something clearly wrong.

The strongest evidence that green is correct is the game itself: in-game
screenshots show the nameplates, dialogue and stage titles **in green**.

So either Kuriimu2 was showing a different file, or it renders these textures
with its own tone handling. **The way to settle it is to export the PNG from
Kuriimu2 and compare it against the same resource exported here** — until that
is done, treat this as open rather than fixed.

### Mipmaps are rebuilt

`texture_levels()` reads how many levels a resource actually stores, and
`patch_texture_rect()` regenerates every lower level from the candidate. A
texture whose top level is English and whose mips are still Japanese reverts
at distance. Verified: the mip tail changes on write (10,752 bytes on a
4-level DXT1, 5,120 on a 3-level DXT5).

A region-limited write still touches **only** the blocks the region covers —
verified with zero stray blocks — while the mips, which cannot be partial, are
rebuilt whole.

### The format code table, settled by looking

The published PC/Switch MT Framework table maps 0x13→BC1, 0x15→BC2, 0x17→BC3,
0x19→BC4. **This big-endian PS3 build does not follow it exactly.** Each code
below was checked by decoding real textures every plausible way and looking at
the result (`XET_FORMATS` in `alrummi3_core.py`):

| code | verdict | evidence |
|---|---|---|
| `0x13` | **DXT1** | A model texture renders correctly as BC1 and as noise as BC4. Previously mis-typed as DXT5, which made **every 0x13 texture fail to decode** — 28 of 28 in a survey. |
| `0x14` | DXT1 | BC1 variant. |
| `0x15` | DXT5 (ambiguous) | BC2 and BC3 decode near-identically on this game's samples. Both are 16 bytes/block, so a donor swap is byte-correct either way. |
| `0x17`, `0x18` | DXT5 | |
| `0x19` | **DXT1**, not BC4 | A water alpha map renders coherently as BC1 and as noise as BC4, so the PS3 build does not use the documented BC4 here. |
| `0x2A`, `0x2B` | DXT5 | Confirmed visually: BC2 gives dithered, broken alpha where BC3 gives the smooth alpha the artwork clearly intends. |

After the fix: **0 decode failures across 3,046 sampled textures** (was 28).

### Mipmaps — the silent half-replacement

**324 of 3,046 sampled textures carry data after the top mip level.** The
original `swap_xet_payload` copied only the top level, which left the source's
smaller mips in place — so the Japanese would still appear at distance. It now
copies from the payload start to the end of the resource when both are the
same length, replacing every mip, and refuses the swap outright when the
source has trailing mips and the donor is a different length.

The ID textures that most of this project touches (`0x2A`, `0x15`) have no
mips — the payload ends exactly at the resource end — which is why the work
done so far is unaffected.

### 3.3 GSM `.msg` messages

Magic `\0GSM`. `u32 unit_count`, `u32 record_count` at offset 8. Record table
at 16: `u32 unit_offset`, `u32 unit_length` per record. The unit array is
`u16` tokens directly after the table.

Token decoding: `0xFFFF` end, `0xFFFE` newline, `0xFFFD` page end, `0xFFFB`
pause, `0xFED2` speaker, `0xFF92` / `0xFF91` colour open/close, other `>= 0xF000`
render as `<CTRL_xxxx>`. Printable glyphs use the ASCII convention
`chr(token + 32)` for tokens 1..94; otherwise a bundled **CSA** table maps
glyph index back to character code.

**CSA**: magic `\0CSA`, `u32` valid count at 4, then `u16` glyph indices from
offset 8 where the array index is the character code.

**FIM**: magic `\0FIM`, `u32 c1`, `u32 c2` at 8. First table is 20 bytes per
record from offset 32; the second is 44 bytes per record and starts with a
`u16` line count and `u16` character count — those are the layout budgets a
translation has to fit.

*Assumed, not proven:* that the control-code list is complete. Unknown codes
are preserved as `<CTRL_xxxx>` tags rather than dropped, which is the safe
behaviour, but a code that turns out to take an argument would mis-render.

### 3.4 What the nameplate art actually looks like

Worth knowing before generating any replacement lettering:

- Nameplates are **transparent-backed** with glyphs floating on them. The RGB
  under fully transparent pixels is magenta `(123, 0, 123, 0)` in **both**
  trees — that is the games' own convention, not corruption.
- Because the background is transparent, "clearing" a region by blurring
  smears the old glyphs into a visible ghost. `_erase_region` checks the
  region's border alpha and erases to the transparent colour instead,
  falling back to blur only for lettering baked onto opaque art.
- The lettering is a **bold italic serif**, roughly Georgia Bold Italic, in a
  bright green sampled at `(121, 255, 121)`. Arial Bold in cream is what made
  earlier generated textures read as obviously wrong. `sample_ink_color`
  now reads the real colour off the source before it is erased.

## 4. Hard rules — do not break these

1. **Never overwrite a source ARC.** Writes always go to a new file.
2. **Verify exactly one entry changed** (`verify_single_replacement`) before
   accepting a write. If more than one moved, the write is wrong.
3. **An audit JSON is written beside every output.** Keep it; it is the only
   record of what was replaced and with what.
4. **Confirmation is a deliberate gate.** Do not auto-tick it, and do not add a
   "write everything" path that skips human review.
5. **DXT1 writes stay blocked** until a fixture-validated encoder exists.
6. **An offline audit does not prove in-engine fit.** After installing a
   confirmed ARC, cold-boot RPCS3 and look at the actual screen.
7. **No cloud calls.** The AI layer is local Ollama or nothing.

## 4d. The dialogue editor

The **Dialogue editor** tab is a port of the project's own proven pipeline
(`rebuild_msg.py`, `pipeline.py`, `build_final2.py`) onto Alrummi 3's ARC
layer, in `msg_edit.py`. Nothing in it was invented.

**The loop.** Open a `rom\jpn\id\msg_m###_pl###.arc`. Every speech is decoded
using the project's per-archive glyph maps and auto-filled from the
dictionary. Filter to *Needs wording*, type the missing lines, sign each off,
then build. Measured on `msg_m019_pl003.arc`: **760 speeches, 660 filled from
the dictionary automatically, 65 needing wording.**

**Live validation** on every keystroke, against the project's conventions:
41-column lines, a 3-line plate ceiling (6 when the Japanese carries hard
breaks, which marks it a briefing), and the 82-character encodable set — an
`&` is flagged because the font has no glyph for it.

**The build** swaps in the Latin TNF, CSA and atlas pages from the Samurai
Heroes donor, rewrites only `\0FIM` secondary column 0 (the reveal budget,
preserving each record's slack), keeps `primary.col4` and `secondary.col8`
byte-identical, and writes empty runs as a single space. It then checks the
**five invariants** and refuses to write if any fails. An audit JSON records
the stats and the invariant results.

Verified: building `msg_m019_pl003.arc` passes all five invariants and comes
out **91.2% identical to the project's own installed build** of the same
archive. The differences are speeches where the dictionary and the project's
per-run batch files disagree — which is what the sign-off step is for.

### `0xFF92` takes ONE argument — the master document is wrong here

This is the one place the master handover document is demonstrably incorrect,
and it is worth knowing because following it corrupts text.

The document lists `0xFF92:2`; the shipped `rebuild_msg.py` says `1`. An
earlier version of this file argued for the document on the grounds that its

| read with `:2` | read with `:1` |
|---|---|
| `tudent of the Honest Satake School` | **S**tudent of the Honest Satake School |

## 4d0. ★ Suggested fix — one button, with an audit

`autofix.py` plus the **★ Suggested fix** button in the header. This exists
because a texture like `roulette_000_ID_HQ` is not one image, it is a **sheet**
— three cards, several badges, a couple of icons, each with its own Japanese.
Styling it gold produces handsome Japanese; there is no donor for it; and
lettering it by hand means finding every element yourself.

The button does the best available thing and then says what that was:

1. **Donor** — an exact-size Samurai Heroes texture for the same resource or
   the same portrait-matched character, copied losslessly. Authoritative.
2. **Sheet repair** — no donor, so segment the texture into its elements, read
   each one, and letter the ones the project dictionary can answer for.
3. **Audit** — every element listed with its box, what it reads, what English
   was found, where that English came from, and whether it was applied.

**Segmentation** uses connected components on the alpha channel with union-find
labelling. Two details make it work on real sheets: these textures sit on a
*semi-transparent field* rather than on nothing, so a naive cutoff merges the
whole sheet into one blob — the threshold is walked down from opaque until the
sheet actually separates; and a region wholly inside another is dropped, or a
card and its own text line would both be lettered and draw twice. The roulette
sheet resolves to **9 elements** in both the jpn and eng trees: three cards,
three badges, the icons.

**Only dictionary-backed wording is applied.** A model translation is recorded
as `model guess` and left for you to accept. Nothing is invented silently.

### Reading the text: two engines, measured

`ocr.py` uses whatever is installed, best first.

| engine | on the roulette sheet |
|---|---|
| **RapidOCR** (ONNX, offline, bundled) | reads 大吉 and 吉 at **0.99–1.00**, whole sheet detected in **0.7 s** |
| **qwen2.5vl** via Ollama | reads more small elements, ~10× slower, no real confidence |

Two findings that mattered more than the engine choice:

1. **The prompt was the bottleneck, not the model.** Asking the vision model
   to transcribe *only* the characters at `temperature 0`, rather than to
   translate, took it from **3 of 9 to 7 of 9**. That was free.
2. **RapidOCR's model is Chinese-trained**, which covers kanji but confuses
   near-identical shapes — it reads 凶 as 区 at 0.97. A small `CONFUSABLES`
   table is tried against the dictionary before giving up, which recovers it.

**A read below `TRUST_THRESHOLD` (0.60) is offered, never applied.** A
dictionary hit built on a shaky read is still shaky, and wrong English on a
texture is worse than leaving the Japanese. Those come back as `needs review`.

Result on the sheet that started this: **5 of 9 elements resolved and lettered
from the dictionary, 2 need review, 2 unresolved**, in 4.4 seconds.

### Lettering keeps the artwork

Erasing a whole element destroyed the card it sat on. `ink_bounds` now finds
where the lettering actually is inside an element, and `erase_ink` fills only
the ink with the **median of the card's own non-ink pixels**, feathered — a
blur was not enough because the blur still contains the glyph and it ghosts
through. The font also shrinks until **whole words fit**, because a size that
cannot fit the longest word hyphenates it into "Fortu / ne".

### 2026-09-10: the sheet route was rebuilt — read this before touching it

The ghosting and the mis-cut elements below were **symptoms of segmenting the
wrong thing**. That is fixed; `sheet.py` replaces the element-finding that
`autofix.find_elements` did, and the notes below are kept only so the old
failure is recognisable if it returns.

**The game ships its own sprite inventory.** Every `id\lsp\...` resource is a
`\0PSL` layout that names each sprite node and the texture it draws from
(`layout.py`). On the roulette sheet that is `waku1`–`waku8` (frames),
`sitaji1`–`sitaji8` (backings), `hanko`, `hanko_kage`, `point`. Across the ROM
this parses **1,119 layouts, version 0x21 throughout, with no failures**, and
`SysRoot` appears exactly 1,119 times — once per layout — which is what says
the name table is being read from the right offset. Useful stems: `moji`
(lettering, 250), `waku` (frame, 179), `kazari` (decoration, 769), `kage`
(shadow), `sitaji` (backing).

The **node records are still not decoded**, so the layout gives names and
counts but not rectangles. `Layout.complete` says so honestly when fewer nodes
were recovered than the header promises (33 header vs 32 recovered on
roulette). Cracking the node array remains the open prize.

**Alpha is the artwork mask on these sheets.** They are drawn in opacity
layers: on the omikuji cards, **44 = the gap between cards, 89 = a card's
translucent backing, 255 = its line art**. So the glyphs and frames separate
themselves at a threshold halfway up, with none of the green-glyph-on-green-
border trouble that defeated every colour rule. `sheet._alpha_ink` does this
and falls back to colour distance on sheets with no such layering.

**Where the lettering is comes from the OCR detector, not a threshold.** It is
a trained model and puts a tight box on each glyph group at 0.94–1.00
confidence. A border sharing the glyph's colour does not fool it.

#### Three bugs, all of which had been masking each other

**Adding numpy bools is logical OR.** The frame filter counted how many crop
edges a component touched with `(a <= x) + (b >= y) + ...`; every term is a
`np.bool_`, so the "count" was only ever `True` or `False` and `touches >= 3`
never held. **That filter was dead code** — which is why several rewrites of
it "produced identical results (18%/26%/2%)". Cast to `int()`. Watch for this
anywhere else a count is built from array comparisons.

**The background sample took in the transparent area outside a card.** When a
detector box reached a card's edge, the rim sample picked up the transparent
magenta beyond it, which inverted the mask and selected *the whole card* as
ink (84.5% coverage on card 1). Only opaque pixels may take part.

**`inpaint()` deliberately preserved the original alpha.** It had a line
reading "the card's own alpha must survive: only the glyph's colour is
replaced", written when ink was assumed to be an RGB matter. Since the glyph
is *defined* by its alpha, keeping that alpha left the old character showing
as a silhouette no matter how well its colour was replaced. Alpha is now
repaired like any other channel.

#### Filling the hole: slide the card over itself

The backings are repeating motifs (asanoha). A blur-based fill can only
average toward a pattern, never reproduce it, so it left the removed character
as a soft tonal seam — that seam was the "ghost", not a mask that was too
small. `asset_gen._shift_fill` searches translations of the card, scores each
on the ring of good pixels around the hole (never on the hole itself), and
copies the motif from the offset that explains those surroundings. Whatever
that offset cannot reach is handed back to the push-pull blur, so a partial
match never leaves a strip of the original glyph behind.

Result on the roulette sheet: **all five assets recognised, translated and
rebuilt**, frames intact, 区 auto-corrected to 凶 through `CONFUSABLES`.

#### What it still cannot do

Card 2's lettering sits high and small in its box, and a faint seam survives
on the largest cards. Sheets whose artwork is *not* opacity-layered fall back
to the colour route and are correspondingly less reliable.

**Two of nine elements read as nothing at all.** Small badges under ~40px
defeat both engines. They are reported `unresolved` and left untouched.

The routes that finish work reliably are the **donor path** and the
**dictionary**; the audit says plainly which elements still need a human, and
nothing is invented to fill the gap.

## 4d1. Material styling — making artwork, not just lettering

`texture_fx.py` is what "polish" should always have been. The old version was
a contrast and sharpness nudge; this is what a layer-style panel does:

* the **alpha channel is a height field** once blurred, so its gradient gives
  a surface normal per pixel;
* lighting is Blinn-Phong against that normal — diffuse for the body of the
  bevel, specular for the highlight along the lit edge;
* colour comes from a **gradient map**: each pixel's luminance indexes a
  256-entry ramp, which is how a flat green card becomes gold without its
  shape changing at all;
* plus inner shadow, inner/outer glow, a gloss sweep, fine grain, and a
  procedural lattice pattern built from three interfering sine waves.

Presets: **Gold medallion, Jade card, Polished silver, Bronze relief, Emerald
glass, Depth only (keep colour)**, with a strength slider. Apply to the whole
texture or to a single repair box; a box style leaves every pixel outside it
byte-identical, which is verified.

It is deterministic numpy and PIL — no model, no download, no network — and
runs in **40–60 ms** on a 512×256 texture. That matters more than it sounds:
results are repeatable, dimensions are preserved exactly, and it cannot invent
a different image each time you press the button.

## 4d2. Repair boxes — fixing part of a texture

Shift+drag on the source adds a numbered **repair box**. Several can be queued
on one texture. With a box selected:

- **Patch box from donor** — copies *just that rectangle* from the loaded
  donor and leaves every other pixel byte-identical. This is the surgical
  repair: one wrong word, one bad corner, without touching good artwork.
  Verified numerically — patching the right half of a 128×128 nameplate left
  the left half exactly equal to the source and the right half exactly equal
  to the donor.
- **Letter this box** — renders the English wording into that box only, in the
  ink colour sampled from the texture itself and a serif italic for banners.
- **Erase box** — clears it the way the artwork is cleared (to the transparent
  colour when the border is transparent, blurred only over opaque art).

Boxes the AI suggests are added to the same list, so a suggested region can be
patched or lettered rather than only typed over.

The result is a candidate like any other, so review and confirmation are
unchanged.

## 4d3. Installing, and getting back out

`install.py` closes the loop the project's own rule demands — that nothing is
proven until RPCS3 is cold-booted.

**Install into game tree…** (below the confirmation) replaces the source
archive with the build, but only after:

1. copying the original into a timestamped folder under
   `_alrummi3_backups/`, and aborting if that copy is not byte-complete;
2. parsing the build and refusing it if the entry count, platform or version
   does not match the file it would replace — a truncated build cannot reach
   the game;
3. recording the install in `install_manifest.json`.

**Installs / revert…** lists every install and restores any of them, or all of
them, from those backups. This does not replace the project's own pre-patch
zips in `_codex_tenka_v6\` — those remain the source of truth for a full
rebuild — but it does mean a single experiment can always be undone.

## 4d4. Dialogue batch — the whole game in one pass

`msg_batch.py` plus the **Dialogue batch** tab survey and build every dialogue
archive. Two deliberately separate passes: survey writes nothing and keeps
only counts, so memory stays flat over a thousand archives; build re-decodes
each archive, verifies the five invariants and writes **only if all five
pass**, refusing and reporting the rest.

### The measured state of the dialogue, 2026-09-10

Surveying all **1,410** archives takes **47 seconds** and reports:

| | |
|---|---|
| speeches | 1,671,239 |
| carrying Japanese | 1,529,409 |
| filled from the dictionary | 1,307,511 |
| already English | 221,610 |
| **genuinely needing wording** | **288** |
| layout problems | 210 |
| archives ready to build | **1,097 of 1,410** |

That is **100.0% covered** — 288 outstanding lines in a million and a half.
Building all 1,097 takes about **6.5 minutes**.

Not ready breaks down as 180 archives with a layout problem, 103 needing

### The lookup bug that hid it

The first survey reported 84.9% coverage and **zero** ready archives. Two
causes, both mine:

1. **`_variants` called `.strip()` before looking up.** Leading and trailing
   spaces are significant — a key like `" 撤退＇"` carries a space where the
   engine substitutes a name at runtime. The raw string is now tried first.
2. **Speeches that are already English were counted as missing.** Plenty of
   the tables are done; `is_already_english()` now separates them, and a
   survey no longer reports work that does not exist.

### Two kinds of untranslated, reported separately

`build_english_archive` distinguishes a speech that was **already English and
passed through untouched** from one that **still held Japanese and lost its
meaning**. Reporting them together made a clean build look like it had
damaged thousands of lines. Both the survey and the build use the same CJK
test, so their numbers agree exactly — verified: survey 0 missing / 5 already
English against build 0 lost / 5 passthrough on the same set.

**Tick-all never selects an archive that is not ready**, because that would
ship transliterated junk where wording is still missing. A not-ready archive
has to be ticked deliberately.

## 4e. Working a whole archive in one pass

**SH donors → "Replace EVERY texture in this ARC…"** takes the open archive
and reports, per texture: ready to replace, already carrying the donor,
matched but weaker, or no donor at all. The plan lands in the Batch tab for
review; the ones with no donor are listed by name in **File notes** so you can
see exactly what still needs lettering.

**File notes** explains the selected resource without you having to remember
the format: what it is, what it is tied to (a GSM's FIM and CSA, a texture's
layout), what else in the archive shares its name, its Samurai Heroes
counterpart with the match distance, and — on the button — **every archive in
both games that carries a resource of that name**. That last one matters: the
officer name plates exist in three places, and changing one copy is not enough.

## 4f. The dialogue loop — what is and is not known

Reported symptom: a line repeats endlessly in every level. The master document
§7 attributes exactly this to a blank run making the record hold one speech
fewer, so the plate waits for characters that never arrive and repeats its
voice clip.

**Measured on the installed archives, that is not what is happening.** A scan
of 40 installed archives (36,380 speeches) found **zero empty runs**. The
reveal budget shows 68% exact, 24.5% over, 7.5% under — but the same profile
appears in a clean rebuild from `rom/jpn` (81.8% exact vs the installed
81.7%), and the "over" cases are lines like `" was KO'd!"` whose budget
legitimately carries slack for a runtime name substitution.

So the budget is **not** the cause, and the blank-run bug is **not** present.
The cause is still unknown. What is ruled out is recorded here so it is not
re-investigated. The scanning code lives in `msg_edit` (`gsm_records`,
`segs_of`, `groups_of`, `dec_en`) if you want to widen the search.

Also ruled out: nothing in this session modified the dialogue archives. All
1,414 of `rom/eng/id/msg_*.arc` are timestamped before the session began.

## 4g. The window itself

The first layout was three fixed columns, which squeezed a 1024-wide texture
into a sliver and truncated the tab labels. It is now:

- **Three draggable panes** (`ttk.PanedWindow`) for browser / preview /
  workspace, and a **fourth divider inside the review tab** so the Japanese
  source and English candidate can be given uneven widths — drag one to full
  width when studying it.
- **Pop-out previews** — the ⧉ button above either preview opens it in its own
  resizable window that keeps redrawing as the candidate changes.
- **Zoom modes**: Fit, 1:1 (one texel per pixel, essential for judging
  lettering) and Fill, plus Ctrl+wheel and a live `x, y  rgba(...)` readout
  under the cursor, which is what makes boxing a region practical.
- **The layout is remembered** in `alrummi3_settings.json` beside the app —
  but only when it is *usable*. See below.
- **A menu bar** (File / View / Tools / Help) so the features are findable
  without hunting through tabs. **Help → What can this do?** summarises the
  whole tool in one dialog.

### Panes cannot be lost — and why that needed fixing

A divider could be dragged to the edge, which collapsed the pane behind it to
nothing with no way back. Worse, that layout was then **saved and restored**,
so the tool came up broken every launch. A real reported state was:

```
"body_sashes":   [556, 2080]   on a 2106-wide window  -> workspace pane 26px
"review_sashes": [0]                                  -> source preview 0px
```

The Japanese source preview and the entire workspace panel were simply gone.

Three guards now, all of them necessary:

1. **`_positions_usable`** rejects any saved layout that would leave a pane
   under `MIN_PANE` (240px), falling back to proportional defaults.
2. **`_capture_layout` refuses to save** a degenerate layout at all, so a bad
   arrangement cannot outlive the session.
3. **`_sash_released`** re-opens any pane a drag squashed, and says so in the
   status bar.

`_restore_layout` also waits for the window to actually have a width before
setting sash positions — setting them on an unmapped window gets them clamped
to nonsense.

**Two further traps, both of which cost a rebuild to find:**

*A fixed delay is not enough.* The frozen build takes longer to reach its
final size than any delay you would pick, so a one-shot re-apply still landed
against a stale width and the browser pane came out at 248px. Defaults are now
re-applied on every `<Configure>` until the operator actually drags a divider,
which is self-correcting whatever the startup timing.

*The autosave was freezing the startup layout.* `_last_layout_save` began at
`0.0`, so the first poll — 120ms after launch — immediately wrote a settings
file describing the half-built window, and from then on the tool treated that
as a deliberate choice. It now starts at `time.time()`, and `_paned_resized`
keys off a real drag (`_sash_touched`) rather than off whether settings exist.

The default split is 28% / 40% / 32%: about **476 / 680 / 544** on a 1720-wide
window. Verified stable across a restart — first run saves `[476, 1156]`, the
second restores exactly the same widths.

Verified from the real broken settings above: the layout is rejected, panes
come back at 458/835/793 and 402/403, a 256×256 texture draws at 365×365, and
1:1 gives exactly scale 1.0.
- **DPI awareness** is declared before Tk starts, so text renders at native
  resolution instead of being bitmap-stretched by Windows on a scaled display.
- The Create texture tab **scrolls**, because it carries the most controls in
  the narrowest pane.
- A **Log tab** keeps a timestamped scrollback of everything the tool reports,
  with copy and clear.

**Keyboard** (F1 lists them): Ctrl+O open ARC, Ctrl+Shift+O open folder,
Ctrl+F search, Ctrl+G generate, Ctrl+D find donors, Ctrl+Enter confirm and
write, Ctrl+L log, Ctrl+0 fit, Ctrl+1 actual size, Ctrl+± zoom.

Generating now always puts the result in front of you: it switches to the
review tab, redraws the candidate pane and any pop-out. Verified across all
modes — polished with and without text, lettering, and a sub-region box — and
the one invalid combination (lettering with no wording) refuses with a message
rather than doing nothing.

## 5b. Samurai Heroes donor matching

`E:\SAMURAI HEROES` is an officially localized build of the same engine, so
the correct English lettering usually already exists as a real texture. This
is the highest-quality path to English art and it beats both the font renderer
and the local model.

**Index.** `build_donor_index` walks the donor tree in parallel and records
every texture entry by resource basename. Measured: **8,055 archives, 32,252
textures, 5,136 unique names, 31 seconds, a 1.4 MB JSON that reloads in
0.03 s.** It is cached beside the app and survives restarts.

**Matching.** Candidates are ranked by name tier, then boosted for living
under an `\eng\` branch or in a same-named archive, and penalised for `\jpn\`.
Every candidate carries the reason it matched, so a wrong donor is visible in
the list rather than after a write. Verified: `cp_name_pl_000_ID_HQ` (伊達政宗)
returns 12 candidates, 5 at the exact source size, the best being the real
`id\texture\eng\cp_name_pl\cp_name_pl_000_ID_HQ` reading "Masamune Date".

**Resize modes**, all of which return exactly the source dimensions:
`Exact size only` (refuses a mismatch rather than silently scaling),
`Fit inside (keep aspect)`, `Stretch to fill`.

**Lossless block copy.** When the donor is used at exact size and both are
XET with matching dimensions and format, `swap_xet_payload` copies the
compressed BC3 blocks straight across and keeps the source header and trailer.
Re-encoding through the BC3 encoder visibly softens already-compressed
lettering; the copy is byte-identical. Verified: written blocks equal donor
blocks exactly, source header preserved. Any resized donor correctly reports
`lossless_block_copy: false` and goes through the encoder instead.

### The two games number their rosters differently — this is the big one

**A zero-candidate result usually means the character was renumbered, not that
he is missing.** An earlier version of this file claimed 佐竹義重 was
Utage-exclusive because a name lookup returned nothing. That was wrong. He is
in Samurai Heroes as `cp_name_pl_028`, "Yoshishige Satake". Samurai Heroes has
`cp_name_pl_000`–`034` (35 characters); Utage renumbers and extends past 105.
Name-based matching only works where the indices happen to coincide.

**Match characters by portrait instead.** `character_map.py` compares
`cp_face_msg` textures between the two trees. The portrait artwork is
*byte-identical* across releases, so every real match lands at signature
distance **0.00** with a runner-up 40–95 away. 37 characters matched.

The identifier hierarchy matters:

- `cp_face_msg` — **unique to a person.** This is the identifier.
- `cp_face_army` — fallback.
- `kamon` — **only unique to a clan.** Masamune Date and Kojuro Katakura both
  return distance 0.00 against the Date crest, which is historically correct
  and useless for identification. Never match on kamon alone.

Build it from the **SH donors** tab ("Match characters across games"). It needs
a local index of the Utage tree, built once and cached as `local_index.json`
(~4.5 MB), then the map itself is a 4.6 KB `character_map.json`. Cross-roster
matches are ranked tier 0, above any name match, and carry their distance in
the reason text so a weak match is visible before a write.

## 6. Build recipe, and the trap that cost hours

```powershell
cd 'E:\Utage Patching New\Alrummi3'
python -m pip install -r requirements.txt
python -m pip install pyinstaller
.\Build_Alrummi3.ps1
```

Output: `dist\Alrummi3.exe`.

**The trap.** PyInstaller silently shipped `_tkinter` but omitted the pure-Python
`tkinter` package, so the EXE started and died with no GUI. Root cause: Tcl on
this machine can *list* its files under AppData but cannot *stat* them, so
PyInstaller's tkinter hook concluded the runtime was absent and excluded it.

**The fix, all four parts, all required:**

1. Copy `tcl\tcl8.6` and `tcl\tk8.6` out of the Python install into
   `.tk-runtime` **before** PyInstaller scans, and point `TCL_LIBRARY` /
   `TK_LIBRARY` at the copies.
2. `--hidden-import tkinter --hidden-import _tkinter`.
3. `--add-binary` for `DLLs\tcl86t.dll` and `DLLs\tk86t.dll`.
4. `--runtime-tmpdir .\Alrummi3_runtime` so the one-file bundle unpacks beside
   the EXE instead of into a temp path.

The build script also copies `ai_extensions` and `updates` next to the EXE, so
the extension points survive one-file packaging.

If the EXE ever launches to nothing again, this is the first thing to check.

## 7. What is actually done

- Open a single ARC, or **Open Folder…** to recursively index every `.arc`
  underneath and switch between them from the archive selector. Verified
  against 11,276 ARC files in the Utage tree. The scan runs on a thread pool
  and shows `Indexing n/total` while it works; results keep sorted order
  regardless of completion order.
- **Shift+drag on the source preview** sets the text region, with a dashed
  green overlay that stays in sync with the X/Y/W/H boxes in both directions.
  Plain drag still pans, because Tk prefers the more specific binding.
- Search and select entries; type labels from hash and name.
- Preview with zoom slider, zoom buttons, drag-pan, scrollbars, and a
  transparency checkerboard.
- Automatic `/jpn` counterpart lookup (`find_jpn_reference` swaps the path or
  resource segment) opened in a reference tab.
- Readable MSG viewer with record boundaries, per-record line/char budgets from
  FIM, and control codes as tags. Exports to `.txt`.
- Candidate generation at **exact source dimensions**, wrapped and outlined
  text on a rounded panel, optional blurred clear of the old glyph area.
- Side-by-side review, loose-image open, PNG export.
- Integrated local chat with the texture context attached.
- Progress/busy indicator on every worker.
- **SH donors tab**: build/refresh the donor index, find ranked donor
  candidates for the selected texture, pick a resize mode, and load a donor as
  the English candidate. Using a donor sets the region to the full texture
  automatically, because a donor replaces the whole thing. See section 5b.
- **Donor preview.** Selecting a donor row shows that texture in the reference
  pane immediately, so you can see what you are proposing before you use it.
  The decoded image is cached during the search, so arrowing through the list
  is instant.
- **Batch tab.** Plan donor replacements across the loaded archives or a whole
  folder, filtered by resource family (default `cp_name_pl,cp_name_army`).
  Every row is a proposal with its evidence; space or double-click toggles it,
  selecting it previews the donor. Only ticked rows are written.
- Confirmation-gated ARC write with single-entry verification and audit JSON.
  The donor path writes the lossless payload when one is available.

### How batch mode respects the review gate

Rows are **pre-ticked only** when the evidence is as strong as it gets: a
tier-0 portrait match, a donor of exactly the source dimensions, a lossless
block copy available, and something actually left to change. Anything weaker
is listed unticked and needs a deliberate decision. "Tick all" refuses to tick
rows that are already applied or cannot be copied losslessly. Batch writes
**only** lossless copies — it will not silently re-encode.

Outputs go to a folder you choose, mirroring the source tree, and the tool
refuses an output path inside the source tree. Each archive is rebuilt once
however many of its entries matched, every write is re-parsed and checked to
have changed exactly the intended entries, and each output gets its own
`.audit.json` recording the donor, the match reason and tier, and before/after
hashes.

**"Already applied" is a first-class result, not a failure.** Running the plan
over `rom\eng\id\friend_*.arc` proposes byte-identical replacements for 27 of
35 matches, because your earlier transplant work already installed exactly
those donors. The tool independently agreeing with prior work is a good sign;
those rows are marked `done` and are not re-written.

## 8. Known gaps and the next queue

### Landed 2026-09-09 (commit `371b61f`, EXE rebuilt)

- Entry names on extended 144-byte-entry archives were truncated at 64 bytes
  instead of the full 128-byte field. Names are now sliced by `name_bytes`.
  Big-endian Utage archives are unaffected; this matters for the extended-name
  variant the parser claims to support.
- Metadata-only parsing reads the header and the entire entry table in one
  open instead of reopening the file for each table read.
- The folder scan is parallel and reports progress. **2.6x on cold cache**
  (2000 archives, 24.2s to 9.2s), measured on disjoint cold subsets — an
  earlier 55x reading was an artifact of the serial pass warming the OS cache.
- Shift+drag region selection with a live overlay.

**Verification that backs those changes.** Metadata-only and full parses agree
field for field across 40 archives. 60/60 identity rebuilds are byte identical
to their source, which is strong evidence the parser and rebuilder are
lossless. Three single-replacement round trips each changed exactly one entry
with dimensions preserved. The rebuilt EXE launches a real Tk window.

### Also landed 2026-09-09 (second pass)

- `suggest_english` no longer returns Japanese in the translation field, and
  implausible AI regions are rejected instead of clipped to 1 pixel. See
  section 5.
- Samurai Heroes donor matching, resize modes, and lossless BC3 block copy.
  See section 5b.

### Still open, roughly in value order

1. Batch/queue mode: apply donors across many archives in one confirmed pass,
   with one audit per write. This is now much more valuable than it was, since
   a donor match is objective and reviewable in bulk. It brushes against hard
   rule 4 — the review gate must stay per-candidate, not per-batch.
2. Nothing verifies a donor is the *right* donor beyond name and size. A
   perceptual check against the source's layout, or a contact sheet of the
   top candidates, would catch a same-named but wrong texture.
3. Fixture-validated DXT1 encoding, then unblock DXT1 writes.
4. LSP/PSL layout inspection beside the texture so overflow is caught during
   review rather than in-game.
5. Undoable candidate history and cumulative package export.
6. For Utage-exclusive content with no donor, the generated lettering is still
   *rendered text on artwork*. It preserves dimensions and reads cleanly, but
   it will not match the original's hand-lettered look, and the local model
   cannot be trusted to romanize the name. Those need a human-supplied string.
